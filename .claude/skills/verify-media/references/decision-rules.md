# 검증 미디어 판정 규칙 (Gate A~D)

모든 게이트는 **변경 파일 목록 + diff 내용**만으로 판정한다. 추측 금지 — 근거가 되는 파일 경로를
판정 결과에 함께 남긴다.

---

## Gate A — 미디어를 만들어야 하는가?

변경 파일 목록을 아래 표로 분류한다. 목록은 세 가지의 **합집합**이다
(BASE 결정 규칙은 SKILL.md Phase 0 — PR base > checkout 출처 > origin/develop):

- `git diff --name-only {BASE}...HEAD` — 커밋된 변경
- `git diff --name-only HEAD` — 커밋 안 된 변경 (staged + unstaged)
- `git ls-files --others --exclude-standard` — untracked 신규 파일

**하나라도 MEDIA 축에 걸리면 생성**, 전부 NO-MEDIA면 생성하지 않는다.

### MEDIA (눈으로 확인해야 하는 변경)

| 신호 | 경로/내용 패턴 |
|------|---------------|
| Compose UI | `**/ui/**/*.kt` 중 `@Composable` 포함, `*Screen.kt`, `*Content.kt`, `*Layout.kt` |
| XML 레이아웃 | `**/res/layout/**`, `**/res/layout-*/**` |
| 드로어블/에셋 | `**/res/drawable*/**`, `**/res/mipmap*/**`, `**/assets/**/*.json` (Lottie) |
| 치수/스타일/테마 | `**/res/values*/dimens.xml`, `styles.xml`, `themes.xml`, `colors.xml` |
| 사용자 노출 문자열 | `**/res/values*/strings.xml` (UI에 보이는 키) |
| 커스텀 뷰 렌더링 | `onDraw`, `onMeasure`, `onLayout`, `Canvas`, `drawRect`, `Modifier.drawBehind` 포함 |
| 애니메이션/모션 | `animateTo`, `Animatable`, `Transition`, `LottieAnimation`, `*.json` (Lottie), `ObjectAnimator` |
| 위젯 | `**/widget/**`, `**/res/xml/*appwidget*.xml` |
| 알림 UI | `NotificationCompat`, 커스텀 노티 레이아웃 |
| 네비게이션/전환 | route 추가·변경, `enterTransition`, `NavHost` |
| 가시 상태를 바꾸는 UiState | `*UiState.kt` 필드 추가/변경이 **화면에 렌더되는** 값일 때 |
| 디자인 검수 | 브랜치명 `design/*`, 또는 커밋 본문의 `피그마: ...node-id=` 규약 — **diff 내용과 무관하게 MEDIA** (SKILL.md 디자인 검수 모드) |

### NO-MEDIA (데이터/로직 — 영상·이미지 불필요)

| 신호 | 경로/내용 패턴 |
|------|---------------|
| Repository/DataSource | `core-mobile/data/**`, `Default*Repository.kt`, `*DataSource.kt` |
| DB | `core-mobile/database/**`, `*DAO.kt`, `*Entity.kt`, 마이그레이션 SQL |
| 네트워크 | `core-mobile/network/**`, `*Api.kt`, `*Dto.kt`, `*Response.kt` |
| 순수 도메인 | `domain-*/**` 중 UI 무관 `*UseCase.kt`, 매퍼(`as*()`) |
| DI | `*Module.kt` (Hilt), `@Provides`/`@Binds` 만 변경 |
| 빌드/설정 | `**/build.gradle.kts`, `gradle/**`, `settings.gradle.kts`, `.github/**` |
| 테스트 | `**/src/test/**`, `**/src/androidTest/**` |
| 문서/스킬 | `**/*.md`, `.claude/**` |
| 로깅/분석 | AppsFlyer·NELO·nClicks 이벤트 전송만 변경 |

### 경계 케이스 판정

| 상황 | 판정 |
|------|------|
| ViewModel/UiState만 변경 | 그 값이 화면에 보이면 MEDIA, 내부 플래그면 NO-MEDIA |
| 로직 수정이지만 **증상이 화면에 나타난 버그** (겹침·깜빡임·잘못된 텍스트) | **MEDIA** — 수정 전/후 비교 필수 |
| Revert 커밋 | 되돌린 대상이 MEDIA였으면 MEDIA |
| 리팩터링(동작 무변) | NO-MEDIA. 단 UI 코드 이동이면 회귀 확인용 단일 이미지 1장 |
| 문자열만 변경 | 해당 문자열이 보이는 화면 단일 이미지 1장 |
| MEDIA + NO-MEDIA 혼재 | MEDIA 축만 대상으로 생성 |

**NO-MEDIA로 판정하면** 캡처를 시도하지 말고 그 근거(분류표의 어느 행인지)를 한 줄로 보고하고 종료한다.

## Gate B — 이미지인가 영상인가?

| 조건 | 산출물 |
|------|--------|
| 정적 레이아웃·색·치수·아이콘·문자열 | **이미지** |
| 시간에 따라 변하는 것 — 애니메이션, Lottie, 전환, 스크롤, 제스처, 로딩 | **영상** |
| 다단계 사용자 플로우(2회 이상 탭이 필요한 시나리오) | **영상** |
| 재현 조건이 까다로운 버그(특정 순서로만 발생) | **영상** — 재현 과정 자체가 근거 |
| 상태가 여러 개지만 각 상태가 정적 (예: 빈 상태/목록/에러) | **이미지 여러 장 → Gate D로 합성 판단** |

판단 불가 시 이미지를 택한다. 이미지가 리뷰 비용이 낮다.

## Gate C — 비교(AS-IS/TO-BE)인가 단일인가?

| 조건 | 산출물 |
|------|--------|
| 기존 동작이 **잘못돼서** 고친 것 (버그·디자인 불일치·QA 지적) | **AS-IS / TO-BE 비교** |
| 기존 UI를 **변경**한 것 (문구·색·간격·배치 수정) | **AS-IS / TO-BE 비교** |
| **신규** 화면·컴포넌트·기능 (이전 상태가 없음) | **단일** |
| 이슈 상황이 아닌 정상 동작 확인 | **단일** |
| Revert | **AS-IS / TO-BE 비교** (revert 전 = AS-IS) |

AS-IS 캡처 방법: 변경 전 리비전(`{BASE}`)으로 빌드한 APK로 먼저 캡처한다.
같은 디바이스·같은 시나리오·같은 시작 상태를 쓴다 — 다르면 비교가 근거로 못 쓰인다.
AS-IS 재현이 불가능하면(선행 데이터 소실 등) 단일로 내리고 그 사유를 캡션에 한 줄로 남긴다.

### 시안 패널 — AS-IS/TO-BE 에 Figma 를 더한 3단

디자인 시안을 향해 맞추는 변경(디자인 검수, 시안 기반 구현·수정)이고 해당 화면의
Figma URL 을 확보할 수 있으면, **시안을 마지막 패널로 더한다**:

- 비교(Gate C 비교 판정) → `AS-IS | TO-BE | Figma 시안`
- 단일(신규 화면) → `TO-BE | Figma 시안`

URL 소스 우선순위: ① `--figma` 인자·사용자가 대화에서 준 URL ② 커밋 메시지의
`피그마: ...node-id=` 줄(`/figma-apply` 규약, `parse_design_commits.py` 로 전수 파싱)
③ 없으면 시안 패널 생략 — 시안 패널은 있으면 좋은 것이지 필수가 아니며,
없다고 사용자에게 URL 을 되묻지 않는다.

**디자인 검수 모드**(브랜치 `design/*` 또는 커밋에 피그마 규약)에서는 반대다:
시안 패널이 **기본**이고, 노드(영역)마다 별도 3단 산출물을 만들며, 파싱 결과 노드가
0개일 때만 사용자에게 URL 을 묻는다.

경계: 시안 ↔ 구현의 픽셀 1:1 판정·오버레이·수치 보정은 design-qa(-states) 의 몫이다.
여기서 시안은 리뷰어가 "무엇을 향해 고친 것인지" 볼 참고 패널이다.

## Gate D — 한 장(한 편)으로 합칠 것인가?

**합친다:**

| 조건 | 배치 |
|------|------|
| AS-IS / TO-BE 쌍 | 좌우(`h`). 세로로 긴 폰 화면이므로 좌우가 기본 |
| 비교 + Figma 시안 패널 | 좌우(`h`) 1행 — `refrow` (시안은 기기 패널 높이에 맞추고, 납작한 컴포넌트 프레임은 캔버스 중앙에 얹는다. pair/grid 금지 — 기기 패널이 뭉개진다) |
| 라이트/다크 같은 변형 쌍 | 좌우(`h`) |
| 같은 화면의 순차 상태 2~4개 | 좌우(`h`), 4개면 2x2 그리드 |
| 잘라낸 세부 영역(크롭) 비교 | 상하(`v`) — 가로로 넓고 낮은 크롭이라 |

**합치지 않는다 (개별 파일):**

| 조건 | 사유 |
|------|------|
| 5개 이상 | 합치면 각 화면이 리뷰 불가 크기로 줄어든다 |
| 서로 다른 화면·기능 | 캡션이 달라야 해서 한 장에 못 담긴다 |
| 합성 후 각 패널 폭이 **300px 미만** | 텍스트가 판독 불가. 개별로 올린다 |
| 세부 픽셀 검증이 목적 (1~2dp 차이) | 크롭 확대 이미지를 별도로 |

**폭 규칙**: 합성 결과 총 폭이 1600px을 넘으면 각 패널을 등비 축소해 총 폭 1600px에 맞춘다.
GitHub PR 본문 렌더 폭이 약 850px이므로 그 이상은 다운스케일되어 낭비다.

**영상 합성**: AS-IS/TO-BE 영상은 좌우 1편으로 합친다. 길이가 다르면 짧은 쪽 마지막 프레임을
복제해 맞춘다. 좌우 병렬이므로 합쳐도 길이는 늘지 않는다 — 합성본도 상한은 2분이다.

다만 AS-IS 와 TO-BE 의 **타이밍이 어긋나면 비교가 안 된다**. 한쪽만 로딩이 길거나 조작 시점이
다르면, 합치기 전에 각각 `trim` 으로 같은 시작점(예: 버튼 탭 직전)에 맞춘다.

## Gate E — 재생성: 기존 미디어와 중복인가?

`.claude/verify-results/{slug}/manifest.json` 이 이미 있으면 **재생성**이다.
새로 찍기 전에 기존 항목을 하나씩 판정한다. 목표는 **작업 끝에 PR 첨부용만 남는 것**이다.

판정은 `manifest.py show` 의 캡션·kind·compare 만 보고 하지 말고, **애매하면 파일을 실제로 열어본다**
(`compose_image.py info` + Read). 캡션이 부실하게 적혀 있는 경우가 있다.

각 기존 항목을 셋 중 하나로 분류한다:

| 분류 | 조건 | 조치 |
|------|------|------|
| **대체(중복)** | 새 산출물이 같은 것을 보여준다 — 같은 화면 + 같은 시나리오/상태 | `manifest.py remove` 로 항목·파일 삭제 후 새로 등록 |
| **유지** | 새 산출물이 다루지 않는 다른 내용이다 | 그대로 둔다. 다시 찍지 않는다 |
| **폐기** | 변경 범위가 줄어 더 이상 근거가 아니다 (그 부분을 되돌렸거나 스코프에서 빠졌다) | `manifest.py remove` 로 삭제. 대체물 없음 |

### 중복인 것 / 아닌 것

**중복이다 (대체):**

- 같은 화면·같은 시나리오를 다시 찍은 것 — 파일명이 달라도 중복이다
- 기존이 단일이고 새것이 그 화면의 AS-IS/TO-BE 비교 — 새것이 상위집합이다
- 기존이 개별 2장이고 새것이 그 둘을 합친 1장 (Gate D 재판정 결과)
- 기존 영상의 핵심 구간만 다시 트림한 것

**중복이 아니다 (유지):**

- 같은 화면이지만 **다른 상태** — 빈 상태 / 목록 / 에러 / 로딩
- 같은 화면이지만 **다른 변형** — 라이트 / 다크, 폰 / 태블릿
- 같은 기능이지만 **다른 화면** — 목록과 상세
- 같은 시나리오지만 **다른 관점** — 전체 화면 1장과 세부 크롭 1장
  (단 세부 크롭이 전체를 대체할 수 있으면 Gate D 를 다시 적용해 하나로 합친다)

판정이 애매하면 **유지가 아니라 대체**를 택한다. 미디어 4개 예산 안에서 중복이 남는 것이
정보가 하나 빠지는 것보다 리뷰에 해롭다. 단 폐기는 되돌릴 수 없으니, 폐기로 분류한 항목은
사용자에게 한 줄로 알린다.

### 재생성 절차

```
0. sets.sh list / sets.sh history 로 기존 세트 확인
   (history = 이미 PR 에 첨부돼 정리된 세트. manifest 만 남아 있다)
1. manifest.py show 로 기존 항목 파악 (+ 애매하면 파일 열어보기)
2. 항목별로 대체 / 유지 / 폐기 분류 → 사용자에게 분류 결과를 표로 보고
3. 대체·폐기 항목: manifest.py remove --dir D --file X
4. 대체 항목만 다시 캡처·합성·등록 (유지 항목은 건드리지 않는다)
5. manifest.py prune --dir D   ← 원본·프레임·이전 회차 잔여물 정리
6. manifest.py validate --dir D
```

`prune` 은 manifest 가 참조하지 않는 파일을 전부 지운다 (`raw-*.png`, `_frames/`, 이전 합성 결과).
`--dry-run` 으로 먼저 확인할 수 있다. 재업로드 시 storage 의 slug 폴더에서도 미참조 파일이
삭제된다 — 이미 발행된 PR 본문은 커밋 SHA 로 고정돼 있어 깨지지 않는다.

## Gate F — 본문 어디에 붙일 것인가 (role)

미디어는 두 종류다. **검증 결과**와 **근거 자료**는 리뷰어가 읽는 시점이 다르다.

| role | 무엇 | 본문 위치 |
|------|------|----------|
| `verify` (기본) | 이 변경으로 화면이 이렇게 됐다 — AS-IS/TO-BE, 동작 확인 | 최하단 `## 검증` |
| `spec` | 왜 이렇게 만들었나의 근거 — 기획 스펙, API 계약, 디자인 시안, 이슈 재현 조건 | 상단 해당 섹션 (기본 `이슈 정보`) |

`spec` 을 하단에 두면 리뷰어가 "왜 이렇게 했나"를 읽는 중에 스크롤을 내려야 한다.
그 자리에 있어야 맥락이 맞는다.

**spec 으로 분류하는 것:**

- 기획/API 스펙 문서 캡처 (응답 표, 에러 코드 목록, 상태 전이도)
- Figma 시안 (구현 결과가 아니라 **기준**으로 제시할 때)
- QA 지적 시트, 이슈 재현 조건 화면
- 참조용 타 앱/기존 동작 캡처

**verify 로 두는 것:**

- 내가 만든 화면의 AS-IS/TO-BE
- 동작 영상
- 회귀 확인 캡처

같은 Figma 이미지라도 **기준으로 보여주면 spec**, 구현과 나란히 비교하면 그 비교 이미지 자체는
`verify` 다. 판단 기준은 "리뷰어가 이걸 언제 보고 싶은가" 다.

등록:

```bash
python3 $SK/manifest.py add --dir $OUT --kind image --file api-spec.png \
  --caption "API 스펙 — 에러 status 표" --role spec
# 다른 섹션에 넣고 싶으면
  --role spec --section "발생 원인"
```

`--section` 은 본문의 `###` 제목과 **정확히** 일치해야 한다. 못 찾으면 경고와 함께 최하단으로
간다. 프로젝트 PR 템플릿 기준 후보는 `이슈 정보` / `발생 원인` / `해결` / `테스트 방법` 이다.

`spec` 은 미디어 4개 예산에서 제외된다 — 검증 결과와 성격이 달라 같이 세지 않는다.

## 산출물 예산

| 항목 | 상한 | 이유 |
|------|------|------|
| PR당 미디어 개수 | 4개 | 그 이상은 리뷰어가 안 본다 |
| 영상(mp4) 길이 | **2분** | 재현 과정이 긴 시나리오가 실제로 있다. 이게 근거의 원본이다 |
| GIF 길이 | **영상 전체** | 인라인 재생되는 유일한 형태다. 아래 "영상과 GIF 의 역할" 참조 |
| GIF 폭 | 400px | 인라인 렌더 폭 + 용량 |
| GIF 용량 | 8MB | 레포 비대화 방지 |
| 이미지 폭 | 1600px | 위 폭 규칙 (업로드 원본 기준) |

본문 **렌더** 크기는 별개다. `verify-media-attach` 가 비율을 보고 `<img width>` 를 정한다
(높이 예산 640px, 그리고 이미지 안 글자가 본문에서 약 10px 로 보이는 폭). 세로로 긴 폰 스크린샷은
288px 폭으로, 글자가 큰 웹 페이지 크롭은 600px 안팎으로, 글자가 작은 격자는 850px 로 렌더된다.
그래서 원본은 판독 가능한 해상도로 두면 되고, 크기 조절을 미리 할 필요가 없다.

상한을 넘길 근거가 있으면 넘겨도 되지만, 넘긴 사유를 보고에 한 줄로 남긴다.

### 영상과 GIF 의 역할

| | 역할 | 길이 |
|---|------|------|
| mp4 | **근거의 원본**. 리뷰어가 클릭해서 받아 본다 | 최대 2분 |
| GIF | **본문에서 실제로 재생되는 것** | **기본 = 영상 전체** |

GHE PR 본문은 `<video>` 태그를 제거한다. 그래서 **리뷰어가 실제로 보는 것은 GIF 뿐**이고,
mp4 는 클릭해야 열리는 링크다. 두 개를 같이 올리고 본문에서는 GIF 를 mp4 링크로 감싼다.

**그래서 GIF 는 자르지 않는 것이 기본이다.** 발췌하면 리뷰어가 흐름의 일부만 보게 되고,
루프가 중간부터 다시 돌아 "영상이 끊겨 보인다"는 오해를 만든다 (실제 리뷰에서 지적된 사례).
검증 영상은 대개 조작 → 결과의 인과를 보여주는 것이라, 결과만 잘라 놓으면 근거가 약해진다.

**제약은 길이가 아니라 용량(8MB)이다.** `compose_video.sh gif` 가 폭·fps 사다리를
내려가며 전체를 담아낸다 (측정: 좌우 비교 82초 → 480px/8fps 846KB).
사다리를 다 써도 안 맞을 때만 자동으로 트림하고 WARN 을 낸다.

**발췌를 택하는 경우** — `--ss/--to` 로 명시한다:

- 재현이 길고(2분 가까이) 변경점이 그 안의 짧은 순간일 때. 전체 루프에서 리뷰어가
  그 순간을 기다려 찾아야 하면 오히려 나쁘다.
- 앞부분이 로딩·로그인 같은 준비 동작으로 길게 채워져 있을 때.

발췌할 때 어디가 핵심인지는 `compose_video.sh frames` 로 프레임을 뽑아 직접 보고 정한다.
발췌하면 본문에 "GIF 는 N초 발췌 — 클릭하면 전체(M분)" 이 자동으로 붙는다.
